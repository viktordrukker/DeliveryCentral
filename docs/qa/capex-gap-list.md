# CAPEX / Capitalisation Report — Completeness Verdict, Gap List & Deactivation Plan

_Source: read-only static trace of `/tmp/dc-fix` (clean origin/main). Date: 2026-06-13._

---

## 1. Overall Verdict

**The CAPEX / Capitalisation feature is FULLY BUILT (schema + read path + logic + UI) — NOT a stub and NOT half-wired. It is, however, INTENTIONALLY PRE-GA and starved of classified data, so it renders all zeros.**

## 2. WHY All Zeros — Single Clearest Root Cause

**Root cause: 100% of approved timesheet hours are classified OPEX because nothing ever sets `TimesheetEntry.capex = true`.**

The report's CAPEX number is the sum of `hours` over `TimesheetEntry` rows where `capex === true`. There are **zero such rows**:

1. `capex` is schema-default `false` (`prisma/schema.prisma:1853`).
2. The **only** write path that can flip it is manual time entry: `TimesheetsService.upsert` uses `dto.capex ?? false` (`src/modules/timesheets/application/timesheets.service.ts:147`) — a per-line user checkbox. There is **no** project-level flag, work-type rule, budget-driven derivation, or rule engine that auto-classifies hours. The platform setting `capitalisation.defaultClassification: 'OPEX'` (`seed.ts:531-533`) is **not consumed** by the write path.
3. The `it-company` seed — the sole profile, generated by `generateItCompanyTimesheets()` — **hardcodes `capex: false` on every single generated entry** (`prisma/seeds/it-company-profile.ts:1540`). This is the only `TimesheetEntry` generator. A grep across `prisma/seed.ts` + `prisma/seeds/*.ts` for any non-false timesheet capex returns **zero hits**.

Consequence chain: `capexHours = 0` for every project → `capexPercent = 0` → `totals.capexPercent = 0` → every `periodTrend` point `capexPercent = 0` → the breakdown table is all-zero / effectively empty → `0 alerts` (reconciliation alerts at `financial.service.ts:147-156` are hours-vs-allocation deviations unrelated to capex, and only fire on real variance).

### Distractor (explicitly ruled out)
The seed **does** set `capex: true` on ~25% of rows at `it-company-profile.ts:1066` — but those are **`WorkEvidence`** rows, a table the capitalisation report **never reads**. Likewise `ProjectBudget.capexBudget/opexBudget` is seeded 40/60 (`:1238-1239`) but is **not** queried by this report. The only `capex=true` data that exists lives in tables the report doesn't touch.

### Secondary note on OPEX also showing 0.0h
OPEX = sum of **all** approved hours in-window and is NOT explained by the classification gap. The seed marks most weeks `APPROVED` (`it-company-profile.ts:1505`) with 5 weekday entries each (:1519-1544), so OPEX should be non-zero on a seeded DB for the default period (`this_month`). If OPEX is genuinely 0 on the live V2 instance, the cause is a **data condition** (could not be empirically confirmed under read-only file access), one of:
- (a) seed not run / `TimesheetWeek` + `TimesheetEntry` empty on that deployment, or
- (b) the selected period has **no APPROVED weeks overlapping** it (e.g. a narrow window catching only `DRAFT` w=0 / `SUBMITTED` w=1 weeks).

The query and aggregation are correct regardless; CAPEX=0 is guaranteed by the data, OPEX=0 requires one of the two conditions above.

## 3. Gap List — what's missing to make CAPEX produce real, trustworthy numbers

### Layer A — Data / Seed (PRIMARY, blocks all CAPEX numbers)
- **A1 (root fix).** No `TimesheetEntry` is ever `capex=true`. Fix in `generateItCompanyTimesheets` (`prisma/seeds/it-company-profile.ts:1540`): set `capex` true on a fraction of entries. Mirror the `WorkEvidence` pattern (`capex: w % 4 === 0`) or derive from `project.engagementModel` / the project's budget split. No schema migration and no service/report code change required — the read path already aggregates correctly.
- **A2.** No migration/backfill flips historical `TimesheetEntry.capex`. If real tenants need CAPEX on existing data, a backfill is needed (none exists; grep of `prisma/migrations` for capex returns only `capexBudget` + the create-column default).

### Layer B — Classification mechanism (DESIGN gap, why data is hard to get right)
- **B1.** Classification is a single manual per-line boolean. There is **no** server-side derivation from project / work-type / budget classification. `capitalisation.defaultClassification` (`seed.ts:531-533`) is declared but **never consumed** by `TimesheetsService.upsert` (`timesheets.service.ts:147`). For trustworthy numbers at scale, a derivation rule (project- or work-type-driven) should populate `capex` rather than relying on every user ticking a checkbox.
- **B2.** The flag description ("OFF until **fiscal calendar** lands", `platform-flags.service.ts:561`) signals an unbuilt dependency: capitalisation is meant to anchor on fiscal periods (`financialFiscalCalendarEntity` flag, default `false`). Until that lands, the period math is calendar-month only, not fiscal — a trustworthiness gap for finance users.

### Layer C — Backend report (NO code gap; hardening only)
- **C1 (optional).** Controller `GET /reports/capitalisation` has no flag guard (`capitalisation.controller.ts:40-57`). With the feature pre-GA, consider gating the endpoint on `reportsCapitalisation` so the API can't be hit while the UI is hidden. Not required for the zeros fix.

### Layer D — Frontend (UX gaps, not the cause of zeros)
- **D1.** No empty-data `EmptyState`. `CapitalisationPage.tsx:291-295` only branches on loading / error / report-null. With `report` non-null but `byProject=[]` and totals 0, it renders the full layout showing `0.0h / 0%` / empty table — making a **data/classification problem look like a built-but-broken report**. Add an empty-data branch ("no capitalised hours in period — classify timesheet lines as CAPEX to populate this report").
- **D2.** Custom-period with blank dates silently no-ops (`CapitalisationPage.tsx:119` guard returns without fetching or surfacing a hint). Edge case.

### Layer E — Flag wiring (the deactivation gap — see §4)
- **E1.** `reportsCapitalisation` defaults OFF in **both** registries, but **nothing enforces it on the V2 surface**: the route-manifest entry `/reports/capitalisation` (`route-manifest.ts:338`) has **no `flag` property** (only `obsoleteInV2: true`), and the CAPEX tab inside the Reports umbrella (`ReportsPage.tsx:62`, rendered :166) is gated **only by role** (`hasAnyRole`), not by `isFeatureEnabled('reportsCapitalisation')`. So the intended "OFF until GA" state is declared but **not honored** — that is exactly why a beta, zero-data report is visible to users in V2.

## 4. Deactivation Plan — turn the feature off cleanly

**Goal:** stop users seeing a beta, all-zeros report. The flag already exists and already defaults OFF in both registries — the only work is to **honor it** on the V2 surface. No flag flip is needed; the defaults are already correct.

### Authoritative flag
| | |
|---|---|
| FE id | `reportsCapitalisation` |
| FE key/default | `flag.feature.reports.capitalisation.enabled` / **`false`** (`frontend/src/lib/feature-flags.ts:160`) |
| BE registry | `platform-flags.service.ts:559-571` — default **`false`**, maturity `beta`, GA `v1.2`, _"OFF until fiscal calendar lands"_ |

### Option 1 (RECOMMENDED — minimal, reuses existing machinery)
Hide the CAPEX tab from the Reports umbrella unless the flag is on. Two small edits, both in `frontend/src/routes/reports/ReportsPage.tsx`:

1. Add a `flag` field to the CAPEX tab def (line 62) and filter the visible tabs on both role **and** flag:
   - line 62: `{ id: 'capitalisation', label: 'CAPEX', description: 'Capitalisation breakdown', allowedRoles: CAPITALISATION_ROLES, flag: 'reportsCapitalisation' },`
   - extend the `ReportsTab` interface (line 51-57) with `flag?: FeatureFlagId;`
   - line 100-103 `visibleTabs`: `TABS.filter((t) => hasAnyRole(...) && (!t.flag || isFeatureEnabled(t.flag)))`
2. Wrap the render at line 166 so a deep-link `?section=capitalisation` while the flag is off shows the standard disabled-module screen instead of the zeros page:
   - `{activeTab === 'capitalisation' ? <FeatureGuard flag="reportsCapitalisation"><CapitalisationPage /></FeatureGuard> : null}`
   - `FeatureGuard` already supports `flag={...}` (`frontend/src/routes/FeatureGuard.tsx:57-67`) and renders the `FeatureNotEnabled` EmptyState — same pattern the `evidence` tab uses. No new component needed.

Because `activeTab` falls back to the first **visible** tab when the requested one isn't visible (`ReportsPage.tsx:104-108`), step 1 alone removes it from the strip and from deep-link selection; step 2 closes the direct-URL hole.

### Option 2 (also gate the standalone route)
The legacy direct route `/reports/capitalisation` (`route-manifest.ts:338`, `router.tsx:405-406`) is already `obsoleteInV2: true` (hidden from the V2 sidebar) but still resolves for deep links/bookmarks. To gate it too:
- add `flag: 'reportsCapitalisation'` to the manifest entry at `route-manifest.ts:338` (the manifest already supports a `flag` field and `routeVisible` composes role+flag — see `route-manifest.ts:80-115`), and/or
- wrap the route element at `router.tsx:405` in `<FeatureGuard flag="reportsCapitalisation">…</FeatureGuard>`.

### Option 3 (belt-and-suspenders — backend)
Gate the controller endpoint on the same flag so the API returns disabled while the UI is hidden (`capitalisation.controller.ts:40`). Optional; the UI gate is sufficient for the user-visible problem.

### Verification after deactivation
- `npm --prefix frontend run test` — update `ReportsPage` tab tests (`ReportsPage.test.tsx`, `ReportsPage.dstabs.test.tsx`) and `route-manifest` tests to expect the CAPEX tab absent when the flag is off / present when forced on (`VITE_FORCE_FLAGS_ON=reportsCapitalisation`).
- Manual: with default flags, `/reports` shows no CAPEX tab; `/reports?section=capitalisation` and `/reports/capitalisation` render the `FeatureNotEnabled` EmptyState, not the zeros report.

### To RE-ENABLE later (for completeness)
Flipping the flag on is **not** enough to show real numbers — gap **A1** must be fixed first (seed/derive real `capex=true` data), ideally with **B1** (server-side derivation) and **B2** (fiscal calendar) so the numbers are trustworthy, plus **D1** (empty-state) so an empty period reads as "no capitalised hours" rather than "broken report".
