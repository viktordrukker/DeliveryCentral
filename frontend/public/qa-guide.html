1 · What DeliveryCentral is

A delivery‑operations platform for IT / professional‑services companies: people, projects, staffing, time & cost, cases, audit, integrations. It replaces a stack of spreadsheets and ad‑hoc tools with one system of record around four primary jobs.

JobOwned byWhere you start
Plan capacity — who is free, whenResource Manager/staffing-desk?view=planner
Staff a project — fill a request with a personPM + RM/staffing-desk?view=requests
Run the work — plan vs. actual, risks, milestonesPM + Delivery Manager/projects/:id, /dashboard
Govern the system — RBAC, integrations, auditAdmin/admin/*

Your accounts are full admin — you can see and do everything any role can.

4 · How to test — the working loop

For each session, work one persona at a time. The aim is realistic, scenario‑based exploration — not exhaustive click‑coverage.

  1. Pick a persona + job from §1.
  2. Log in (or "View as") that persona.
  3. Walk the happy path end‑to‑end. Note any friction, confusing labels, or 2+ click detours.
  4. Walk one edge case (empty data, filter to zero, slowest path, error case).
  5. Check the four UX guardrails as you go (below).
  6. Log findings — one GitHub Issue per finding.

The four UX guardrails (use as a checklist)

  • Every page has a forward action — no dead‑ends.
  • Filters survive a back‑button round‑trip.
  • Every KPI on a dashboard is clickable.
  • You never have to scroll to find the Approve / Resolve button.

Priority of what to look for

  1. Broken happy path — a core flow (login, create project, staff a request, submit timesheet, run a report) fails or 500s. P0
  2. Wrong data — number on a dashboard ≠ the list it links to. P1
  3. RBAC leak / lockout — a role sees something it shouldn't, or can't reach something it must. P0
  4. UX friction — pages that violate one of the four guardrails. P2
  5. Copy / labels — confusing or inconsistent wording. P3
  6. Performance — anything > 3s to load (excluding exports). P2
  7. Missing feature — a job the product wants to support but doesn't. File as a feature proposal.
What NOT to file: 2‑px cosmetic tweaks (unless readability breaks), "should work like Jira/Workday" comparisons, anything you can't reproduce on a second try. Reproduce, write steps, then file.

6 · Etiquette

  • Stay on staging. Don't poke at any prod host even if creds appear in chat.
  • Don't share your password. Each account is per‑person. Reusing one defeats the audit trail.
  • One finding per issue. Don't bundle 5 unrelated bugs in one ticket.
  • Search before filing. is:open <keyword> on the issues tab to avoid duplicates.
  • Reference your seed data. If you used QA-anna-2026-05-21 as a project name, mention it — reproduction becomes trivial.

How to file a bug, issue, or feature proposal

Repo: github.com/viktordrukker/DeliveryCentral

30‑second version

  1. Reproduce it twice.
  2. Take a screenshot or short screencast.
  3. Open a new issue.
  4. Pick the right template below (Bug / UX / Feature), paste, fill it out.
  5. Add labels (see §13).
  6. Submit. Do not assign yourself — the maintainer triages.

7 · Pre‑flight checklist

  • I can reproduce it (closed tab, re‑ran, still happens).
  • I have numbered steps from a known starting state.
  • I searched existing issues — no duplicate.
  • I copied the URL from the browser at the point of failure.
  • I know the persona (my QA account, or a "View as" identity).
  • I have evidence — screenshot or screencast.
  • It's one finding (split if there are two).

If any box is unchecked — stop and fix that first.

8 · How to file

Via the GitHub web UI

  1. Go to issues/new/choose (or just issues/new).
  2. Title — use the title formula below.
  3. Body — paste the matching template and fill it in.
  4. Labels (right sidebar) — pick from §13.
  5. Attachments — drag‑drop screenshots/videos into the body. For files > 10 MB, upload elsewhere and link.
  6. Click Submit new issue and note the issue number.

Via the gh CLI (optional)

gh issue create \
  --repo viktordrukker/DeliveryCentral \
  --title "[bug][P1][area:staffing] Auto-match returns 0 candidates when 'Frontend' filter is applied" \
  --label "bug,qa-finding,area:staffing,severity:p1" \
  --body-file /tmp/my-finding.md

10 · Title formula

[<type>][<priority>][area:<module>] <short, specific summary in present tense>
  • <type> — bug, ux, feature, doc, perf
  • <priority> — P0–P3 for bugs; omit for feature/ux/doc.
  • area:<module> — closest match: dashboard, staffing, projects, timesheets, cases, org, admin, auth, integrations, reports, audit.

Good titles

  • [bug][P1][area:staffing] Auto-match returns 0 candidates when "Frontend" filter is applied
  • [bug][P2][area:dashboard] KPI "Open requests" shows 7, drilldown list has 5 rows
  • [ux][area:projects] Risk-add button forces scroll on /projects/:id (L4)
  • [feature][area:reports] Export planner grid to XLSX

Bad titles (don't)

  • Bug — useless
  • Staffing is broken — vague
  • One run‑on sentence with five qualifiers — no shape, no actionability

12 · Lifecycle — what happens to your issue

  1. Open — you filed it.
  2. Triage — maintainer reads, may ask for clarification. Respond fast (same day) while context is fresh.
  3. Accepted — added to docs/planning/MASTER_TRACKER.md or directly into a sprint.
  4. In progress — linked to a PR.
  5. Closed via PR — fix is merged. Re‑verify on staging within 2 working days. If still broken, reopen with RE‑OPENED: prefixed to the comment and fresh repro steps.

If an issue is closed as duplicate, wontfix, or invalid — read the closing comment. Don't refile. If you disagree, comment on the closed issue and tag Viktor.

13 · Worked example — end‑to‑end
